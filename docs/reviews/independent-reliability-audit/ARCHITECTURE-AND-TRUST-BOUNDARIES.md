# Architecture and trust boundaries

`apps/desktop/src/CheckoutPanel.tsx:203` builds/retains an operation and awaits native prepare, post and response; it displays saved only after a native response. `apps/desktop/src-tauri/src/main.rs` exposes command handlers into the `Workspace`/`Store` boundary. `packages/local-store/src/payments.rs:1290` opens an immediate transaction, checks native permissions, compares durable request/operation identity, calls `billing::post_into`, writes the retail outcome/outbox and commits. `billing.rs:149` records invoice, stock, ledgers, credit, payment, audit and billing outbox in that transaction. Ordinary cash/credit use the billing transaction (`billing.rs:373`); SQLite/SQLCipher is the authority, renderer totals are previews.

Prepare and final acknowledgement are separate transactions. Lost replies can leave an uncertain, durable pending request; the same request is retried or its saved result recovered. A commit failure rolls back the transaction; actual hardware power-loss guarantees are not established. The store serializes writers and checks revisions, but concurrent flows are only proven for tested paths. `identity.rs` checks native principal, role and scope; renderer flags are not authority. `recovery/` handles archives; `receipt-print.ts` creates a browser print job. Optional replication, GST, LAN and Android were not integrated or assessed exhaustively.
