# Restaurant checkout source increment

Base: published Phase 13 at 209ab4e1521ab676f27270039b403842c4c8c32d. Target dependency: feature/phase13-restaurant-operations (#158). No merges or CI workflow dispatches.

The new native binding assigns one retail checkout operation to each restaurant order. Preparing persists the exact actor-owned retail request and its order binding in one writer transaction. Restaurant posting calls the existing retail engine. Its existing billing transaction now writes the restaurant settlement reference after the invoice/stock/ledger/outbox writes. Any later failure in the enclosing retail transaction rolls back the invoice and settlement together. The active-table index excludes settled orders only after that reference exists. SQLite refuses settlement without the bound invoice and prevents reassignment of a settled order.

The menu maps each priced variant or add-on to a distinct existing catalog product, with category, label, variant and availability. The native ticket handler loads the available menu entry and catalog price; renderer-provided prices and names are not authoritative. Accepted ticket prices and notes remain in the native ticket snapshot. Legacy unpriced tickets are refused at checkout. A changed catalog price is explicitly refused; this increment does not silently reprice or override the existing checkout engine. Paid add-ons are separate billable product lines; free preparation modifiers use notes. Grouped required/optional modifier selection is not implemented.

The desktop restaurant panel has menu configuration, variant/add-on selection, payment allocations (cash, UPI, card, credit), customer ID, tax input, durable recovery and the existing invoice/receipt component. Done acknowledges the native retail checkpoint before the next sale. Digital payment entries are recorded intents, never gateway verification or external charges. Table/order references remain in native bindings; they are not yet printed on the invoice. KOT printing and a kitchen print spool remain pending. Discounts are not newly implemented.

Focused checks: desktop TypeScript/Vite build; 16 accepted-price/split-allocation tests; 38 desktop native-command/capability contracts; 92 schema/migration/invariant checks; restaurant SQLite binding uniqueness, invoice prerequisite, rollback and table-release checks. These do not execute Rust, SQLCipher, native RBAC or financial transaction replay. Cargo is unavailable, and Windows/Apple installed-app acceptance was not attempted.

Release blockers: native compilation and financial execution on this exact source, fault injection across prepare/post/restart, concurrent cashier tests, backup/restore upgrades, installed receipt printing and installer lifecycle acceptance. The inherited macOS dependency lock regeneration is still required. A bound checkout that is definitively refused after stock/credit/catalog changes currently needs native recovery work; changing or cancelling the binding to edit allocations is not implemented. Another cashier cannot take over the binding. These limitations must be resolved before production use.

Recommended next increment: native checkout amendment/takeover for definitively refused unpaid orders, keeping the operation ID and proving no invoice exists under the writer lock; then table/order receipt metadata and KOT printing. Do not distribute this as a production restaurant release.
