## Stage 4 of the second hardening pass: the index is now a regression gate

Before this pass, IV2-004 was evidenced by recorded numbers and by two benchmark
scripts (`bench-replication-lookup.mjs`, `bench-replication-index-variants.mjs`)
that nothing in the verify chain ran. A later change could have dropped or
reshaped the index and every gate would still have gone green.

`verify:replication-postgres` now proves the plan, its cause, and its
restorability inside one always-rolled-back transaction on a dedicated
connection (so the durable schema the other checks share is untouched):

  1. the shipped schema still carries both composite UNIQUE constraints on
     events, each leading with business_id, restore_generation — i.e. the lookup
     still cannot be served by a constraint;
  2. `events_operation_identity` exists, keys on (business_id, stream,
     operation_id, event_pk) and does NOT key on restore_generation;
  3. with 40k probe rows present, the lookup for an operation ingested behind the
     whole backlog is served by that index and examines <= 4 rows;
  4. DROP INDEX inside the transaction removes it from the plan and the same
     lookup now examines O(table) rows (>= 10k, > 100x) and is slower — the
     dependency is measured, not assumed;
  5. re-applying the shipped migration restores the index and the fast plan
     (also the idempotency guarantee);
  6. after the rollback there are zero probe rows and the index is present on the
     durable schema.

### The gate catches the regressions it exists for

Three mutations of the shipped migration were applied and each was caught:

  | mutation | gate output |
  |---|---|
  | index removed entirely | "the shipped events_operation_identity index exists" fails |
  | (business_id, operation_id, stream, event_pk) | "keys on the semantic identity and ends in event_pk" fails |
  | keyed on restore_generation | same check fails (wrong identity) |

The migration file was restored from a saved copy after each mutation and the
working tree confirmed clean.

### What this does not claim

The plan-shape assertions are deterministic and are the real gate. The timing
comparison (indexed vs degraded) is recorded but only asserted as a relative
inequality, and the benchmark in docs/reviews/iv2-004-replication-lookup-performance.md
keeps its warm-cache / single-client limitation. Nothing here is a production
load test.
